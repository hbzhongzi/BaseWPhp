# “今天要做什么饭”后端接口落地说明

## 1. 文档范围

本文根据 `今天要做什么饭-示例.html` 原型整理，用于指导该小程序后端接口、数据库和联调落地。

HTML 仅是交互原型，不是后端实现要求。原型中的 `FOODS`、`history`、`book`、`drawCount`、`enabled` 和 `localStorage` 都是浏览器内存/本地状态；正式小程序接入后应由服务端按小程序项目和用户保存、校验和返回。

本模块遵循项目公共接口基线：

```text
/api/{programKey}/v1
```

除健康检查、启动配置外，以下接口均需要 `Authorization: Bearer <access_token>`。所有数据查询必须同时限定可信 `program_id` 和当前用户 `user_id`，不能接受客户端传入的 `program_id`。

## 2. 原型功能与后端模块对应

| 原型功能 | 后端模块 | 是否需要接口 |
| --- | --- | --- |
| 转盘抽取 | 抽取模块 | 是，服务端随机选择并记录结果 |
| 盲盒抽取 | 抽取模块 | 是，与转盘共享奖池和抽取记录 |
| 奖池设置 | 奖池模块 | 是，读取、保存当前用户的启用美食 |
| 美食图鉴 | 图鉴模块 | 是，查询用户已抽到的美食和次数 |
| 做法科普弹层 | 美食内容模块 | 是，读取美食详情、起源、步骤和小贴士 |
| 个人中心 | 用户与统计模块 | 是，读取用户资料和抽取统计 |
| 建议收集 | 反馈模块 | 是，提交功能建议、Bug、推荐美食和其他反馈 |
| 分享小程序 | 微信小程序客户端能力 | 否，使用小程序分享配置 |
| 关于小程序 | 启动配置/客户端静态信息 | 可选，不单独建接口 |

## 3. 统一请求与响应

### 3.1 请求头

```text
Authorization: Bearer <access_token>
X-Request-Id: <可选，服务端未收到时自动生成>
Content-Type: application/json
```

`{programKey}` 由路由确定小程序身份。客户端不得通过 JSON 传入 `program_id`、`user_id`、`draw_count`、`is_enabled` 等系统字段。

### 3.2 成功响应

```json
{
  "code": 0,
  "message": "success",
  "data": {},
  "timestamp": 1793351360,
  "request_id": "5f0c2f9b7d704fc99e7a6c6cbf9fb8b1"
}
```

### 3.3 错误码建议

| HTTP | 业务码 | 场景 |
| ---: | ---: | --- |
| 401 | `40100` | 未提供登录凭证 |
| 401 | `40101` | 登录凭证无效或已过期 |
| 404 | `40400` | 美食、记录或资源不存在 |
| 409 | `40900` | 幂等键重复或状态冲突 |
| 422 | `42200` | 参数校验失败 |
| 422 | `42201` | 奖池至少需要启用一项 |
| 429 | `42900` | 抽取或反馈提交过于频繁 |
| 500 | `50000` | 服务内部错误 |

## 4. 美食内容模块

### 4.1 数据职责

美食内容是平台维护的基础数据，包含原型 `FOODS` 中的 12 项：火锅、烧烤、麻辣烫、寿司、披萨、汉堡、沙拉、牛肉面、饺子、盖浇饭、炒饭、螺蛳粉。

内容字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | bigint | 美食 ID |
| `name` | string | 美食名称，小程序内唯一 |
| `emoji` | string | 展示图标；生产环境可增加 `image_url` |
| `description` | string | 简短描述，对应原型 `desc` |
| `origin` | text | 起源小知识 |
| `steps` | array<string> | 家常做法步骤 |
| `tip` | text | 科普小贴士 |
| `status` | integer | `1` 启用，`0` 停用 |
| `sort` | integer | 默认排序 |
| `created_at` / `updated_at` | datetime | 时间字段 |

### 4.2 接口

#### `GET /api/{programKey}/v1/foods`

获取当前小程序可参与奖池的美食列表。默认只返回 `status=1` 的内容。

可选参数：

| 参数 | 类型 | 说明 |
| --- | --- | --- |
| `status` | integer | 管理端可传；小程序端禁止读取停用内容 |
| `keyword` | string | 按名称搜索，最大 50 字符 |
| `page` / `page_size` | integer | 管理端分页参数；小程序端可直接返回少量启用列表 |

成功数据建议：

```json
{
  "items": [
    {
      "id": 1,
      "name": "火锅",
      "emoji": "🍲",
      "description": "约上三五好友，热气腾腾最热闹。",
      "enabled": true
    }
  ],
  "total": 12
}
```

`enabled` 表示当前用户奖池状态，不是平台美食的 `status`。服务端根据当前用户配置计算，客户端不能直接修改平台 `status`。

#### `GET /api/{programKey}/v1/foods/{food_id}`

获取美食详情，用于图鉴详情弹层。返回 `origin`、`steps`、`tip` 和基础展示字段。

## 5. 奖池模块

### 5.1 业务规则

- 新用户默认启用全部可用美食。
- 奖池是当前用户在当前小程序内的配置，不跨小程序共享。
- 保存时至少启用一项；停用平台已下架美食时，读取和抽取时自动排除。
- 原型的“全选”和“重置”是前端编辑动作，后端只接收最终启用 ID 集合。
- 保存配置时使用覆盖语义，避免重复追加。

### 5.2 接口

#### `GET /api/{programKey}/v1/food-pool`

获取当前奖池。

```json
{
  "enabled_food_ids": [1, 2, 3],
  "enabled_count": 3,
  "total_count": 12,
  "items": [
    { "id": 1, "name": "火锅", "emoji": "🍲", "enabled": true }
  ]
}
```

#### `PUT /api/{programKey}/v1/food-pool`

保存当前用户奖池。

请求体：

```json
{
  "food_ids": [1, 2, 3],
  "idempotency_key": "pool-20261030-001"
}
```

校验：数组不能为空、ID 必须是当前小程序可用美食、单次数量不得超过平台上限。建议使用 `(program_id, user_id, food_id)` 唯一键，并在事务中删除旧配置后批量写入新配置。

## 6. 抽取模块

### 6.1 业务规则

- 转盘和盲盒只是展示方式，均从当前用户已启用奖池中随机选择。
- 随机结果必须由服务端产生，不能以客户端随机结果作为最终结果。
- 服务端先读取奖池，再生成抽取记录；奖池为空时返回 `42201`。
- 抽取成功后增加用户抽取次数，增加对应图鉴计数，并更新最近抽取记录。
- 抽取、统计和图鉴计数应在一个数据库事务内完成。
- `mode` 仅允许 `wheel`、`box`；保留字段用于统计和运营分析。
- 建议支持幂等键，网络重试不得重复增加抽取次数。

### 6.2 接口

#### `POST /api/{programKey}/v1/food-draws`

请求体：

```json
{
  "mode": "wheel",
  "idempotency_key": "draw-20261030-0001"
}
```

成功数据：

```json
{
  "draw_id": 10001,
  "mode": "wheel",
  "food": {
    "id": 1,
    "name": "火锅",
    "emoji": "🍲",
    "description": "约上三五好友，热气腾腾最热闹。"
  },
  "draw_count": 8,
  "book_count": 4,
  "drawn_at": "2026-10-30 18:30:00"
}
```

错误处理：奖池为空返回 `42201`；同一 `idempotency_key` 重试时返回第一次结果；短时间频繁抽取返回 `42900`，具体频率由运营配置决定。

#### `GET /api/{programKey}/v1/food-draws`

查询用户抽取历史，支持 `page`、`page_size`、`mode` 和日期范围筛选。只返回当前用户数据。

```json
{
  "items": [
    {
      "draw_id": 10001,
      "mode": "wheel",
      "food_id": 1,
      "food_name": "火锅",
      "drawn_at": "2026-10-30 18:30:00"
    }
  ],
  "total": 8,
  "page": 1,
  "page_size": 20
}
```

## 7. 图鉴模块

### 7.1 业务规则

- 图鉴由抽取记录聚合得到，不能由客户端直接提交次数。
- 一个用户对同一美食只保留一条聚合记录，`draw_count` 每次抽中加一。
- 已抽到过的美食才出现在图鉴；详情内容从美食内容模块读取。
- 停用美食可以保留在历史图鉴中，但应标识 `status=inactive`，不能继续进入奖池。

### 7.2 接口

#### `GET /api/{programKey}/v1/food-book`

获取当前用户图鉴。支持 `page`、`page_size`；默认按最近抽到时间倒序。

```json
{
  "items": [
    {
      "food_id": 1,
      "name": "火锅",
      "emoji": "🍲",
      "draw_count": 3,
      "first_drawn_at": "2026-10-01 12:00:00",
      "last_drawn_at": "2026-10-30 18:30:00",
      "status": "active"
    }
  ],
  "collected_count": 4,
  "total_food_count": 12,
  "page": 1,
  "page_size": 20
}
```

#### `GET /api/{programKey}/v1/food-book/{food_id}`

获取用户是否收集、抽取次数和美食做法详情。未收集时可返回 `40400`，或由产品确认是否允许查看全量科普；默认按“图鉴已收集后查看”设计。

## 8. 用户与统计模块

### 8.1 `GET /api/{programKey}/v1/users/me`

复用公共用户接口，返回用户资料。该页面的称号和副标题可以由前端根据 `draw_count` 计算，也可以由服务端返回等级字段；推荐返回原始统计，避免前后端等级规则不一致：

```json
{
  "id": 10001,
  "nickname": "美食萌新",
  "avatar_url": null,
  "draw_count": 8,
  "book_count": 4,
  "total_food_count": 12,
  "title": "美食探索家",
  "subtitle": "吃得越来越明白啦"
}
```

称号规则可配置为：`0-4` 美食萌新、`5-14` 美食探索家、`15-29` 美食达人、`30+` 美食宗师。规则一旦由服务端输出，客户端不应另行覆盖。

### 8.2 `GET /api/{programKey}/v1/food-stats`

获取抽取和收集统计，供个人中心和运营分析使用：

```json
{
  "draw_count": 8,
  "book_count": 4,
  "total_food_count": 12,
  "last_drawn_at": "2026-10-30 18:30:00"
}
```

## 9. 反馈模块

### 9.1 业务规则

- 类型固定为 `feature`、`bug`、`food_recommendation`、`other`；前端展示文案分别为功能建议、Bug反馈、推荐美食、其他。
- 内容必填，建议长度 1-2000 字；服务端做敏感词、频率和重复提交校验。
- 推荐美食可以单独增加 `food_name` 字段，也可以暂时写入 `content`；推荐使用独立字段便于运营处理。
- 反馈默认状态为 `pending`，后台处理后变更为 `processing`、`resolved` 或 `rejected`。
- 反馈日志不得记录 access token 和完整个人隐私信息。

### 9.2 `POST /api/{programKey}/v1/feedback`

请求体：

```json
{
  "type": "feature",
  "content": "希望增加晚餐推荐筛选",
  "food_name": null,
  "contact": null,
  "idempotency_key": "feedback-20261030-0001"
}
```

成功数据：

```json
{
  "feedback_id": 30001,
  "status": "pending",
  "created_at": "2026-10-30 18:35:00"
}
```

## 10. 数据库设计

以下表均使用项目现有数据库前缀规则，并建议增加公共字段 `created_at`、`updated_at`。除平台内容表外，用户数据表必须包含 `program_id`。

### 10.1 `mini_food` 美食内容表

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| `id` | BIGINT UNSIGNED | PK | 美食 ID |
| `program_id` | BIGINT UNSIGNED | NOT NULL | 所属小程序；若平台共享，仍用于发布范围控制 |
| `name` | VARCHAR(64) | NOT NULL | 美食名称 |
| `emoji` | VARCHAR(16) | NULL | Emoji 展示 |
| `image_url` | VARCHAR(512) | NULL | 可选图片 |
| `description` | VARCHAR(255) | NOT NULL | 简介 |
| `origin` | TEXT | NULL | 起源知识 |
| `steps` | JSON | NOT NULL | 步骤数组 |
| `tip` | TEXT | NULL | 科普贴士 |
| `status` | TINYINT | DEFAULT 1 | `1` 启用，`0` 停用 |
| `sort` | INT | DEFAULT 0 | 排序 |

唯一索引建议：`uk_program_food_name(program_id, name)`；索引：`idx_program_status(program_id, status, sort)`。

### 10.2 `mini_food_pool` 用户奖池表

| 字段 | 类型 | 约束 | 说明 |

| `id` | BIGINT UNSIGNED | PK | 主键 |

| `food_id` | BIGINT UNSIGNED | NOT NULL | 美食 ID |
| `created_at` / `updated_at` | DATETIME | NOT NULL | 时间字段 |

唯一索引：`uk_program_user_food(program_id, user_id, food_id)`。

### 10.3 `mini_food_draw` 抽取记录表

| 字段 | 类型 | 约束 | 说明 |

| `request_id` | VARCHAR(128) | NULL | 请求追踪 ID |

### 10.4 `mini_food_book` 用户图鉴聚合表

| 字段 | 类型 | 约束 | 说明 |

## 11. 事务、并发与安全

1. 抽取接口使用数据库事务：锁定/读取有效奖池，生成结果，写入抽取记录，更新图鉴和统计；任一步骤失败都回滚。
2. 抽取随机选择在服务端完成。可以使用密码学安全随机数或数据库安全随机方案，不能信任客户端传来的 `food_id` 作为抽中结果。
3. 奖池更新与抽取并发时，以提交成功时的奖池快照为准，并在响应中返回最终 `food`；不要让前端动画决定结果。
4. 所有接口按 `program_id + user_id` 做数据隔离；用户不能读取或删除其他小程序、其他用户的抽取记录和反馈。
5. 反馈和抽取都需要限流；建议按用户、IP、项目三维度设置阈值，并在日志中记录 `request_id`、路由、状态和耗时，不记录 Token 或完整请求正文。
6. `steps` 使用 JSON 数组存储和返回，后台编辑时限制单步长度、总步骤数和 HTML 标签，避免把原型文本直接当作可执行 HTML 输出。

## 12. 开发落地顺序

1. 配置小程序注册项和数据库中的 `sys_mini_program`，确认 `program_id`。
2. 建立美食内容管理和初始化数据，将 HTML 的 12 项 `FOODS` 转换为数据库种子数据。
3. 实现奖池读取/覆盖保存，再实现服务端抽取和幂等记录。
4. 从抽取记录更新图鉴聚合和个人统计。
5. 实现美食详情、反馈提交和后台反馈处理。
6. 为每个接口补充成功、参数错误、未登录、跨项目隔离、重复请求、空奖池和并发测试。
7. 接入小程序前端时，删除前端 `localStorage` 作为事实来源的逻辑，改为以接口返回为准；转盘动画只负责展示服务端已经返回的结果。

## 13. 验收清单

- [ ] 新用户首次读取奖池时默认拥有全部启用美食。
- [ ] 奖池不能保存为空，非法/停用美食 ID 会被拒绝。
- [ ] 转盘和盲盒都从服务端奖池抽取，且结果写入抽取记录。
- [ ] 同一幂等键重试不会增加两次抽取次数或产生两条反馈。
- [ ] 图鉴次数与抽取记录聚合结果一致。
- [ ] 美食详情包含简介、起源、步骤和小贴士，并正确限制内容长度。
- [ ] 个人中心统计只属于当前小程序和当前用户。
- [ ] 反馈类型、内容长度、频率和敏感内容校验有效。
- [ ] 响应包含 `request_id`，日志可按小程序和日期定位。
- [ ] 跨小程序、跨用户 ID 猜测和停用美食访问均无法越权。

## 14. 与现有公共接口的关系

本文接口属于某个小程序的业务域，建议实现于：

```text
app/mini/{programKey}/controller/v1/
app/mini/{programKey}/service/
app/mini/{programKey}/model/
```
